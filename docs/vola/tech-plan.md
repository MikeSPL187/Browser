# Технический план: наследство Candy и обновления GeckoView (2026-09-29)

## 1. Разгрузка BrowserController без большого рефакторинга

**Что есть.** `browser/BrowserController.kt`: 16 262 строки, около 700 функций (352 публичных),
111 наблюдаемых состояний Compose, 20+ колбэков в конструкторе. Через него идут вкладки, Gecko,
внешние приложения, профили, загрузки, разрешения, поиск на странице, избранное, отложенные вкладки.
Логика правил уже частично вынесена в чистые объекты `*Rules`, и они покрыты тестами.

**Правило бойскаута.** Каждый PR, который меняет поведение в какой-то области `BrowserController`,
выносит эту область целиком в отдельный контроллер. Отдельных PR «только рефакторинг» нет.

1. **Контроллер фичи** — обычный класс со своим состоянием (`StateFlow` или Compose state) и
   узким API, например `FindInPageController`, `DownloadsController`, `PermissionsController`,
   `TabsController`, `WorkspacesController`, `CredentialsController`. Зависимости передаются
   через конструктор как порты, а не как `Activity`.
2. **Мост совместимости.** Старые методы `BrowserController` становятся однострочными делегатами
   с `@Deprecated(ReplaceWith(...))`. Вызывающий код переезжает постепенно, в тех же PR.
3. **Тесты.** Контроллер фичи покрыт JVM-тестами в `app/src/test` (движок подменяется
   фейковой реализацией порта).
4. **Храповик в CI.** Скрипт `scripts/ci/size_ratchet.py` хранит в `scripts/ci/size-baseline.json`
   число строк `BrowserController.kt`, `MainActivity.kt`, `ui/BrowserScreen.kt`. Если PR их
   увеличивает, CI падает. Если уменьшает, скрипт предлагает обновить базовую линию. Размер растёт
   только вниз.

**Порядок выноса** совпадает с порядком переноса дизайна (раздел 4), поэтому отдельной работы
не появляется:

| PR дизайна | Что выносится из BrowserController |
| --- | --- |
| Адресная панель-остров | `AddressBarController`: ввод, подсказки, прогресс, капсула при прокрутке |
| Обзор вкладок и пространства | `TabsController`, `WorkspacesController` |
| Новая вкладка и Essentials | `EssentialsController` (закреплённые сайты, редактирование) |
| Меню и сведения о сайте | `SiteInfoController`, `PermissionsController` |
| Пароли | `CredentialsController` поверх порта `CredentialVault` |
| Загрузки, поиск на странице | `DownloadsController`, `FindInPageController` |

Ожидаемый результат: через 8–10 фичевых PR `BrowserController` уменьшится примерно вдвое и
станет координатором жизненного цикла движка и вкладок.

## 2. Настройки: сто параметров → понятная структура

**Что есть.** 15 страниц настроек (~4 900 строк Compose), 87 ключей в `BrowserSessionStore`,
плюс отдельные настройки разработчика. Поиск по настройкам и видимость по движку разбросаны по
страницам.

**Подход — тоже постепенный:**

1. **Реестр настроек.** Каждая настройка описывается декларативно: `SettingSpec(key, type,
   default, title, summary, section, level, visibleWhen, keywords)`. Интерфейс строится из
   описаний, поиск идёт по ним же, тесты проверяют умолчания и сохранение.
2. **Страница переезжает на реестр,** когда PR её трогает. Первая — «Внешний вид» (её всё равно
   переделываем под новые токены).
3. **Три уровня:** «Основные» (до 7 строк на странице), «Дополнительно» (свёрнуто), «Для
   разработчиков» (только в debug и preview). Каждая переезжающая настройка получает решение:
   оставить, убрать в «Дополнительно» или удалить с миграцией значения.
4. **Новая структура** из макетов: Пароли · Приватность · Синхронизация · Перенос /
   Внешний вид · Пространства · Вкладки и жесты · Поиск / Расширения · Перевод · Загрузки.
5. **Движок:** если настройка недоступна в WebView-сборке, она скрывается через `visibleWhen`,
   а не показывается выключенной.

## 3. Регулярное обновление GeckoView

**Каденс.** По сообщениям СМИ, с Firefox 155 (1 сентября 2026) Mozilla экспериментально
выпускает мажорные версии Firefox для компьютеров и Android **раз в две недели**, а не раз в
четыре. Номера сходятся: GeckoView 156 вышел в сентябре, nightly 158 — уже 12 сентября.
Точный календарь — на whattrainisitnow.com (из облачной среды он закрыт, проверить можно с
телефона). Процесс ниже рассчитан на две недели и работает и при четырёх.

1. **Автоматический PR.** Воркфлоу `geckoview-update.yml` (сделан в Q2) **каждый день** читает
   `maven-metadata.xml` артефакта `org.mozilla.geckoview:geckoview` на maven.mozilla.org
   (`scripts/ci/geckoview_latest.py`). Если вышла новая стабильная версия, он пушит ветку
   `geckoview/<версия>` с правкой `gradle/libs.versions.toml` и открывает PR
   `build: GeckoView <версия>` с меткой `screenshots`. В описании: заметки о выпуске, изменения
   API GeckoView, бюллетени безопасности (MFSA) и чек-лист на телефоне. Старые PR GeckoView
   закрываются как заменённые. *Build* и *Screenshots* воркфлоу запускает сам: PR, открытый
   через `GITHUB_TOKEN`, их не запускает.
   - Dependabot GeckoView больше не трогает (`ignore`). Реестр Mozilla у него настроен, но
     проверка раз в неделю не укладывается в 48 часов для точечных выпусков, и в его PR нет
     чек-листа.
   - Нужна настройка владельца: *Settings → Actions → General → Allow GitHub Actions to create and
     approve pull requests*. Без неё воркфлоу пушит ветку и падает с подсказкой.
2. **Проверка в PR:** сборка, юнит-тесты, lint, скриншоты с эмулятора, дымовые инструментальные
   тесты. Ручная проверка на телефоне по чек-листу: 5 сайтов, видео и картинка в картинке,
   вход с паролем, приватная вкладка, uBlock Origin работает.
3. **Сроки:** точечные обновления безопасности (156.0.1 и т. п.) — в течение 48 часов,
   мажорные — в течение недели. Версии не пропускаем: в каждой есть исправления уязвимостей.
4. **Устаревшие API.** Предупреждения `@Deprecated` из GeckoView собираются в сводку сборки.
   Mozilla удаляет устаревшие API через несколько версий, при двухнедельном цикле это быстро.
   Каждое такое предупреждение становится задачей в ближайшем PR.
5. **Если сборка сломалась:** PR обновления не сливается, пока не зелёный. Исправление идёт
   в тот же PR, по правилу 1 `CLAUDE.md` — только внутри адаптера Gecko.

Реализация — Q2 (#32).

### PR 1 подробно: токены темы v4

1. **Цвет.** Расширить `design/tools/gencss.mjs`: кроме CSS выводить Kotlin-файл
   `ui/theme/VolaSchemes.kt` со схемами для всех восьми `WorkspaceAccent` и приватного режима.
   - Для каждого: светлая, тёмная (фон `#000000`) и повышенный контраст, плюс ореол и
     ok/warn.
   - Файл генерируется и коммитится, библиотека цвета в приложение не попадает (новой
     зависимости нет).
   - Проверка контраста — тот же `contrast.py` или юнит-тест на Kotlin.
2. **`VolaTheme`.** Собирает `ColorScheme` из выбранного пространства.
   - Добавляет `VolaExtendedColors` (ореол, ok/warn, карточка) через `CompositionLocal`.
   - Ведёт оформление «Рама»/«Воздух»: новая настройка `BrowserChromeStyle` (`Frame`, `Air`),
     по умолчанию `Frame`, в `shared/.../data/AppearanceSettings.kt`.
   - Тёмная тема всегда чистый чёрный. `BrowserAppearanceMode.Amoled` читается как `Dark`
     (сохранённое значение `amoled` мигрирует), пункт OLED из настроек убирается.
3. **Шрифты.** Manrope и Literata (OFL) вшиваются в `res/font` как variable TTF с лицензиями.
   - `Typography` повторяет шкалу `.ty-*` из `vola4.css`.
   - Шрифты не загружаются из сети.
4. **Форма, отступы, тени, движение.**
   - `Shapes` (8/12/16/20/28), константы `VolaSpacing`, `VolaElevation`.
   - `VolaMotion` — пружины `spring(dampingRatio, stiffness)` из доски Tokens.
5. **Превью.** `VolaThemePreviews.kt` показывает три пространства в светлой и тёмной теме.
   - Существующие экраны продолжают работать на новых токенах без переделки разметки.
