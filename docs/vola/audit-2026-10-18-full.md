### N-01 · Низкий (мёртвый код) · Немецкая страница синхронизации в `shared` — удалена
`shared/…/shared/ui/settings/SyncSettingsPage.kt` (513 строк, 43 немецких литерала: «Synchronisierung», «Server-Adresse»,
«Verbinden»…) была заготовкой для iOS-приложения (`iosApp/` в репозитории уже нет) и **нигде не использовалась**.
**Поправка к первой версии отчёта:** я утверждал, что страница видна пользователям планшета через
`ui/SettingsScreen.kt:502`. Это было **неверно**: тот вызов ведёт на `app/.../ui/SyncSettingsPage.kt` (тот же пакет,
42 `stringResource`, локализована), а на немецкую страницу не импортировал никто — я принял одно имя за один файл и не
проверил импорты. Пользовательского дефекта не было; был мёртвый код с литералами, которые гейт `literals` и нашёл.
**Сделано (по слову владельца «удаляй»):** удалены файл и его тест `SyncSettingsFormRulesTest` (проверял только правила
этой страницы), правка `docs/sync/app-integration.md`. Дерево теперь без единого литерала: тест
`test_repository_has_no_findings` в `LiteralsTest` держит это для всех будущих правок.

### N-02 · Средний (продукт) · История ограничена 250 записями
`data/BrowsingLibrary.kt:54`: `MAX_HISTORY_ENTRIES = 250`, обрезка в `addHistory` (`:67`). Ни `decisions.md`, ни план
v5 такого лимита не обосновывают — это наследство Candy. Цель «Safari» (поиск по истории, «вернуться к странице
месяц назад») с 250 записями недостижима. Лимит не поднять без переезда: история лежит одной JSON-строкой в
`SharedPreferences` и переписывается целиком синхронным `commit()` на каждый переход (это и есть V-07).
**Исправление:** перенести историю в уже существующий SQLite-слой (`RecallRepository`), индексировать по времени и
профилю, убрать лимит (или поставить 100 тыс.), писать вне главного потока. Закрывает V-07 и N-02 одним шагом.

### N-14 · Низкий–средний · Передача по QR (V26): три слабости сокетного слоя
Сам протокол (`LocalTransferProtocol`) безупречен: ключ идёт только через экран, HMAC-доказательство, AEAD с привязкой к
сессии и nonce запроса, строгий разбор, только частные IPv4. Слабости — в `browser/transfer/AndroidLocalTransferPort.kt`:
- **(а) Один медленный клиент подвешивает предложение.** `serve()` принимает подключения по одному, а `soTimeout` (5 с)
  действует на каждое чтение, а не на весь запрос (`LocalTransferHttp.readLine` читает по байту, до 1 024 байт на строку
  и 32 заголовка). Устройство в той же Wi-Fi, узнавшее порт, может слать по байту раз в 4,9 с и держать соединение
  десятки минут; срок жизни (120 с) проверяется только между подключениями, так что предложение переживает срок, а
  получатель стоит в очереди. Конфиденциальность не страдает (без ключа ответа не получить), страдает доступность.
  **Исправление:** общий срок на подключение (например, 5 с на весь запрос) и проверка срока внутри чтения.
- **(б) Пять любых неверных запросов закрывают предложение** (`LocalTransferOffer.MAX_WRONG_REQUESTS = 5`; запрос на
  чужой путь тоже считается). Ограничение защищает 256-битный ключ от подбора, который невозможен, но даёт любому в сети
  «выключатель» предложения: пять `GET /` — и передача сорвана («Слишком много попыток»). **Исправление:** считать только
  запросы на верный путь с неверным доказательством или убрать лимит; ключ подобрать нельзя в любом случае.
- **(в) `receive()` без Wi-Fi идёт мимо привязки к сети.** `clientSocket = { Socket().also { wifiNetwork(connectivity)?.bindSocket(it) } }`:
  если Wi-Fi нет (мобильные данные, VPN), `?.` молча пропускает привязку, и запрос к частному адресу из кода уходит через
  маршрут по умолчанию — в том числе в корпоративный VPN (слепой запрос на адрес и порт, заданные QR-кодом). Кроме
  того `bindSocket` бросает `IOException`, если сеть пропала между сканированием и подключением, а `receive()` вызывает
  `clientSocket()` в потоке вызывающего (`BrowserSyncSettingsV5.kt:295` — главный поток) без `try`: возможен вылет.
  **Исправление:** без Wi-Fi-сети — сразу `Unavailable`; создание и привязку сокета — в рабочий поток под `runCatching`.

### N-15 · Низкий · `CandySyncRepository`: потокобезопасность держится на соглашении
Работу сериализует однопоточный исполнитель, но `observe()`, `close()`, `currentState()` и флаги `startRealtime/stopRealtime`
обращаются к `state`, `listeners`, `realtimeConnection` из потока вызывающего, без `@Volatile` и блокировок. `close()` на
главном потоке закрывает соединение, пока поток синхронизации может его открывать: соединение остаётся открытым после
закрытия репозитория. Вероятность малая (закрытие происходит при выходе), ущерб — утечка сокета и устаревшие данные.
**Исправление:** `@Volatile` для `state`, копирование при записи для `listeners`, а `close()` — через `dispatch`.
